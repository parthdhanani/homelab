Step 4 — Provision VPS

Terminal (Mac) — if not done in Step 3
cd ~/cryptex-rebuild/terraform
terraform init
terraform apply
terraform init fails with "context deadline exceeded"? The provider is already cached locally. Use:
terraform init -upgrade=false
Or skip init entirely and run terraform apply directly — if the provider is already in .terraform/providers/ it works without hitting the registry.
Tearing down / destroying the VPS: Always use terraform destroy — never terminate via the OCI console. Terraform manages the full resource tree (VCN, subnet, internet gateway, boot volume). Manual console termination leaves the boot volume orphaned and billable.

preserve_boot_volume = false is already set in terraform/main.tf — the boot volume is permanently deleted when you run terraform destroy. No manual cleanup needed.

Note the public IP from the output. Cloud-init then runs automatically (~5 min):

  • Installs Docker, Docker Compose, rclone, fail2ban
  • Configures iptables (SSH only inbound), IPv6 disabled
  • Creates /opt/cryptex/ directory tree
  • Reboots once complete

Pre-configured filters (6 blocklists, 2 allowlists):
  • Hagezi Pro++ — comprehensive ad/tracker blocking (~750k rules). Includes popup blocking — no separate popup list needed.
  • OISD Small — complementary coverage (~70k rules, different domain set from Pro++). Adds what Pro++ misses without memory bloat.
  • Hagezi NRD 14-Day — blocks newly registered domains (phishing/malware delivery)
  • NextDNS CNAME Cloaking — blocks tracker CNAME redirect chains
  • HaGeZi TIF Medium — threat intelligence feeds (malware, C2 servers)
  • AdGuard Mobile Ads — mobile-specific ad servers
Why not Hagezi Ultimate? Pro++ has minimal false positives. Ultimate blocks everything including native trackers — requires active allowlist maintenance. Pro++ is the right tradeoff for a self-hosted setup.
Why no Unbound? Quad9 handles DNSSEC validation and recursive resolution. Adding Unbound would use ~100MB extra RAM, add another container, and increase DNS latency (cold cache). The VPS is in Oracle's datacenter — there's no ISP snooping risk, so DoH upstream isn't needed either.

Updating AdGuard Config After Initial Setup

The initial config is deployed automatically by deploy.sh. To apply template changes to a running VPS without going through the UI — and without losing your admin account — use the dedicated update script:

VPS — Apply updated AdGuard config from template
cd /opt/cryptex && ./scripts/update-adguard.sh

This script: backs up the live config → merges template changes → preserves your admin users and custom rewrites → recreates the container with updated memory limits → waits for healthy status. Rollback is automatic (backup path printed on screen).

"DNS server is starting up" in the AdGuard UI?
This happens when the container restarts or filter lists are downloading. Causes:
  • Memory pressure — too many large filter lists. Solution: use OISD Small (not Big), update interval 12h (not 1h). Already configured correctly.
  • Container restart — Docker OOM killer or health check failure. Check: docker logs cryptex-adguard --tail 20
  • Filter list refresh — normal during the 12-hour update cycle. Wait 30–60 seconds.
"AdBlock Detected" wall on some websites?
Some sites run JavaScript to check if ad domains are reachable. If DNS blocks them, the site shows a gate. This is expected — it means filtering is working.

Fix options:
  • Per-site whitelist — add @@||site.com^ in Filters → Custom Filtering Rules. The site's ads will show but it will function.
  • uBlock Origin browser extension (recommended) — works at browser level, can bypass most anti-adblock walls. Complements DNS blocking: DNS handles all apps (not just browser), uBlock handles browser-level walls + cosmetic filtering.
DNS blocking alone cannot bypass JavaScript-based anti-adblock detection.

13. SCORM Auto-Deploy Pipeline

LOCAL MAC → Git → n8n → Moodle

Publish SCORM courses directly from a Git repo on your Mac to Moodle — bypasses Cloudflare's 100MB upload limit entirely.

How it works

  1. Push SCORM .zip + metadata.json to Forgejo
  2. Forgejo webhook triggers 09-scorm-deploy n8n workflow
  3. n8n saves the .zip to the shared moodle-uploads volume
  4. n8n runs docker exec cryptex-moodle php scorm-import.php
  5. PHP CLI creates/updates the SCORM activity in Moodle's database directly
  6. Telegram confirmation with direct Moodle course URL

  "title": "Module 1: Introduction"
}

Cloudflare Zero Trust: Allow DoH Without Auth

DoH clients can't do browser-based authentication. You must add a Bypass policy for the DNS query path:

Cloudflare Zero Trust → Access → Applications
Application: dns.YOUR_DOMAIN
Policy 1 (Bypass):   Path = /dns-query*   → Action: Bypass  ← allows DoH queries without auth
Policy 2 (Allow):    Everything else      → Action: Allow   ← protects the admin UI

Without Policy 1, DoH queries return a 302 redirect to the login page → DNS fails → no internet.

Two DNS options (pick one or both):
  • Tailscale DNS — automatic when connected to Tailscale. No profile needed. Encrypted via WireGuard. Set nameserver 172.18.0.12 in Tailscale admin → Override local DNS.
  • DoH Profile — works everywhere (even without Tailscale). Routes DNS via CF Tunnel → AdGuard. Use when Tailscale is off.

sleep 10
